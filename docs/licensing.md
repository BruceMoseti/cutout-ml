# Licensing

Two questions matter for a segmentation project, and only one of them is about the code:

1. **Can I use the software?** Yes — MIT, see [`LICENSE`](../LICENSE).
2. **Can I use the *weights*?** This is the question that sinks most background-removal
   projects, and it is the reason this repository trains its own. Answer: yes, MIT, for
   every checkpoint it produces.

Per-architecture attribution — papers, upstream repositories, which implementations are
independent and which are shape-compatible with published checkpoints — is in
[`docs/models.md`](models.md). This document covers the project-level position: what you
own, what you inherit, and what you have to check yourself.

## The weights problem, and why it is a problem

Segmentation and matting models are the awkward case in open-source ML licensing. The
*code* is almost always permissive; the *weights* frequently are not, and the two are
published together in a way that makes it easy to miss:

- **U²-Net** — code Apache-2.0, official weights Apache-2.0. Clean.
- **BiRefNet** — code MIT, but several widely-mirrored third-party fine-tunes are
  released under non-commercial terms. A checkpoint pulled from a random model hub is
  not automatically usable in a product.
- **The commercial background removers** — their models are not licensed for
  redistribution at all.
- **The datasets underneath them** are the deeper issue. DUTS, DIS5K and AM-2k are
  distributed for research use. A model trained on a research-only dataset carries that
  restriction into whatever it is used for, and "the weights are Apache-2.0" does not
  wash it out.

The practical consequence is that the licence of a shipped background remover is
determined by its training data far more than by its source tree, and that provenance is
usually undocumented.

## What this repository owns

**Every checkpoint here is trained from scratch, in this repository, on data generated by
this repository.** There is no pretrained initialisation anywhere: no ImageNet backbone,
no distillation from a larger model, no fine-tuning of a downloaded checkpoint. The
training data is procedurally synthesised by `src/cutoutml/datasets/procedural.py` from a
single integer seed — no photographs, no scraped images, no third-party annotations.

So the licence chain is short and entirely inside this repository:

| Artefact | Licence | Why |
|---|---|---|
| Source code | MIT | This repository. |
| CutoutNet architecture (tiny/small/base) | MIT | Designed here; not derived from a published model. |
| Trained CutoutNet checkpoints | MIT | Trained here, on data generated here. |
| ONNX exports of those checkpoints | MIT | Derived from the above. |
| The synthetic dataset and its generator | MIT | Generated by code in this repository. |
| Training run records (`training/runs/*.json`) | MIT | Produced here; committed as provenance. |
| Benchmark results (`benchmarks/results/*.json`) | MIT | Produced here. |
| U²-Net / BiRefNet **reimplementations** | Apache-2.0 / MIT respectively | Independent implementations from published descriptions; the upstream licence is carried through out of respect for the origin. See [`docs/models.md`](models.md). |
| Upstream U²-Net / BiRefNet **weights** | *not included* | Never committed, never downloaded implicitly. Anyone who fetches them inherits their terms — including the terms of the data they were fitted to; see below. |

One asymmetry deserves stating plainly, because it is the whole point of the exercise. The
U²-Net weight files are Apache-2.0, and that covers the files. It does not cover **DUTS**,
the research-use dataset their authors trained them on. A deployment that downloads
`u2net.onnx` and serves predictions from it is therefore in a materially different
position from one that serves CutoutNet, even though both artefacts end up in `models/`
and both are nominally permissive. `python -m cutoutml.models.download_weights` prints the
licence of what it is about to fetch for exactly this reason.

This is also why the benchmark tables label the pretrained rows as out-of-domain rather
than simply reporting them as the best available accuracy: those numbers come from a model
whose provenance a commercial user has to evaluate separately.

This is the direct payoff of the constraint recorded in
[ADR-004](decisions/ADR-004-synthetic-dataset.md). The synthetic dataset was chosen
because no real dataset could be downloaded in the environment this was built in, and its
accuracy numbers are consequently not comparable to published DUTS or DIS5K results — a
genuine cost, stated plainly in [`docs/benchmarks.md`](benchmarks.md). But it also means
the weights have no upstream at all, which is a licensing position no
fine-tuned-from-a-download project can offer.

## Dependencies

Read from installed package metadata rather than transcribed from memory, so it describes
the versions actually resolved in this environment. Regenerate it with:

```bash
.venv/bin/python -c 'from importlib.metadata import metadata as m; \
import sys; [print(f"{p:24}", m(p)["Version"], m(p).get("License-Expression")) \
for p in sys.argv[1:]]' torch numpy psycopg    # ...or whichever packages
```

### psycopg is LGPL, and that is worth understanding rather than ignoring

`psycopg` (version 3) is LGPL-3.0-only, unlike almost everything else here. For the way
this project uses it — imported as a Python library by an application that is deployed,
not distributed — the copyleft obligations are not triggered in the way they would be for
a statically linked C binary: the LGPL's requirement is that recipients can replace the
library, and a `pip install` of a different psycopg satisfies that.

Two cases still deserve care:

- **Distributing a self-contained binary or image** that bundles psycopg means shipping
  an LGPL component, and the LGPL's relinking provisions apply to that artefact.
- **Modifying psycopg itself** means publishing those modifications under the LGPL.

If neither is acceptable, `pg8000` (BSD-3-Clause) is a drop-in alternative at the
SQLAlchemy URL level: change `postgresql+psycopg://` to `postgresql+pg8000://` in
`CUTOUTML_DATABASE_URL`. Nothing in this codebase depends on psycopg-specific behaviour.

### ffmpeg is a subprocess, not a library

The video pipeline invokes `ffmpeg` and `ffprobe` as child processes
(`src/cutoutml/pipelines/ffmpeg.py`) and never links against libav*. This is a
deliberate licensing decision as much as an operational one: ffmpeg builds are
LGPL-2.1+ or GPL-2+ depending on which encoders were enabled at compile time, and a
build with `--enable-gpl` (which most distribution packages use, and which is required
for x264) makes anything *linked* to it GPL. Calling a separate executable across a
process boundary is not linking, so the GPL does not propagate into this codebase.

The consequence for an operator is that the ffmpeg binary is yours to choose. A build
without `--enable-gpl` cannot encode H.264 via libx264, which is what the MP4 composite
path uses; that is a capability trade-off to make deliberately, and
`GET /health/ready` reports which alpha-capable containers the installed build actually
delivers so the answer is observable rather than assumed.

## If you are evaluating this for commercial use

- The code and every weight file it produces are MIT. No attribution beyond the MIT
  notice is required, and no field-of-use restriction applies.
- Do not run `python -m cutoutml.models.download_weights` and then assume the result is
  MIT. It prints the licence of what it is about to fetch, for exactly this reason.
- If you retrain on your own data, the resulting weights inherit whatever your data
  permits — that is the same trap described at the top of this document, and this
  repository cannot protect you from it.
- If you swap in a real dataset (`--dataset-root`, see
  [`docs/benchmarks.md`](benchmarks.md)), check its terms. DUTS, DIS5K and AM-2k are
  research-use.
- Replace psycopg if you intend to distribute a bundled artefact, as described above.

## Patents

None of the algorithms implemented here are, to the author's knowledge, encumbered by an
active patent. GrabCut (Rother et al., 2004) and spectral-residual saliency (Hou & Zhang,
2007) are both used via published descriptions and, in GrabCut's case, OpenCV's
Apache-2.0 implementation, which carries an explicit patent grant. This is a statement of
belief and diligence, not legal advice.

## This is not legal advice

The analysis above is the author's reading of the licences involved, recorded so that the
reasoning is inspectable rather than implied. If the answer matters commercially, have a
lawyer read it.
